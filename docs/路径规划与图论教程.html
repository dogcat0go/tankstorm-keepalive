从国战地图学图论：路径规划与最短路径

这个仓库里有一个真实的路径规划问题：人在某座城，要打另一座城，中间要经过哪些城、先占领哪些城。本文用这份代码当教材，从「什么是图」讲到「Dijkstra 为什么是对的」，再到「计划赶不上变化时怎么重算」。所有例子都跑在游戏的真实地图上（95 座城、140 条道路），可以动手点。

1. 问题从哪来

国战里，玩家站在一座城，只能攻击同城或相邻城里的人。要打远处的目标，就得一座城一座城地挪过去。挪动的规则（都是抓包和实盘确认的，见 tankstorm/citydb.py 的 plan_route 注释）：

免费通过

归属国是自己的城

可以直接走过去落脚，也可以当走廊。walk_to 甚至会把连续的本国城「一次走到最远」。

要先占领

别国的城

得先把城里的敌人打空、发一次占领（type:4），才能落脚或借道。每占一座就多花行动力和时间。

禁行

别国的首都与大城

城市编号第 2 位是 1 或 2 的城（fort_locked），不是自己国家就不能占领、也不能借道。原属黑暗联盟（21）的例外。

于是「怎么打到目标城」就变成了一个明确的优化问题：

目标 从当前城出发，找到一个落点（目标城本身或它的任意邻城），使沿途须占领的城最少；占领数相同时，步数最少。禁行的城不能进，已知打不过的城也绕开。

这正是图论里的最短路径问题，只是「最短」的定义不是米，而是一个二元组 (须占领数, 步数)。下面从头搭起来。

2. 图、点、边、邻接表

把每座城看成一个顶点（vertex / node），两座相邻的城之间画一条边（edge），整张地图就是一个图（graph）。这份地图有 95 个顶点、140 条边。

2.1 数据长什么样

顶点和边来自官方 CDN 的 CityData_*.dat，一张 GBK 编码的 TSV，最后一列 nearCity 就是「这座城连着哪些城」：

每一行「城 → 它的邻居列表」，这种存法叫邻接表（adjacency list）。另一种存法是 95×95 的邻接矩阵，格子里 1 表示相连。矩阵占 9025 格却只有 280 个 1，太稀疏，所以稀疏图几乎都用邻接表。

2.2 代码里怎么建图

citydb.city_map() 把 SQLite 里的城市表读成一个 dict，键是城市 ID，值里有 near（邻居集合）和 owner（当前归属国：有占领记录用记录，没有用原属国）：

2.4 地图的结构

  3. 第二圈：9319–9330 十二座城，以及 4 座 buff 城 73xx。

3. BFS：最少步数

先解决最简单的版本：不管归属、不管占领，只问「最少走几步能到」。这是无权图上的最短路，标准解法是广度优先搜索（Breadth-First Search）。

想法像水面上的波纹：从起点出发，先访问所有 1 步能到的城，再访问所有 2 步能到的城……第一次碰到目标时，走过的步数一定是最少的，因为所有步数更少的城都已经在之前的波纹里看过了。

BFS 骨架（Python）from collections import deque

def bfs(g, here, target):
    prev = {here: None}          # 记录每座城是从哪座城走过来的；也兼任「访问过」标记
    q = deque([here])
    while q:
        u = q.popleft()          # 先进先出：保证按步数从小到大处理
        if u == target:
            break
        for v in g[u]["near"]:
            if v not in prev:      # 没见过才入队；第一次见到就是最短
                prev[v] = u
                q.append(v)
    # 从 target 沿 prev 倒着走回 here，再反转，就是路径
    path, cur = [], target
    while cur is not None:
        path.append(cur)
        cur = prev[cur]
    return path[::-1]
两个关键点 ① 队列是先进先出（FIFO），所以出队顺序就是发现顺序，也就是按步数分层。② prev 字典一物两用：既标记「访问过」，又留下回溯的「面包屑」。项目里 plan_route 的 prev 正是这个用法。

在下面的沙盘里选「BFS（只算步数）」，按「单步」看波纹一层层扩开：先是起点的邻居，再是邻居的邻居。

4. Dijkstra：带代价的最短路

BFS 假设每一步代价相同。可现实是：走进本国的城几乎免费，走进敌城要先打仗再占领。不同的边有不同的代价，这时 BFS 的「先发现的就是最短」不再成立，需要 Dijkstra 算法。

4.1 核心思想

BFS 用「先进先出」保证按步数从小到大处理；Dijkstra 把队列换成优先队列（最小堆），保证按累计代价从小到大处理。每次取出代价最小的城 u，它的代价就定死了（不会再变小），然后用它去更新邻居：

松弛（relax） 对每个邻居 v：如果「到 u 的代价 + 边 u→v 的代价」比目前已知的「到 v 的代价」更小，就更新它，并把 v 以新代价推进堆。

为什么取出的那个「定死了」？因为所有边代价 ≥ 0，堆里剩下的每个城代价都 ≥ u，再往后走只会更大，不可能绕出一条更便宜的路回到 u。这就是 Dijkstra 要求边权非负的原因。

4.2 项目里的实现

这是 plan_route 的主循环，去掉注释后不到 20 行。请对照上面的描述逐行读：

tankstorm/citydb.py · plan_route()pq = [(0, 0, here)]          # 堆里的元素：(须占领数, 步数, 城市)
best = {here: (0, 0)}        # 每座城目前已知的最小代价
prev = {here: None}          # 回溯用
found = None
while pq:
    occ, hops, u = heapq.heappop(pq)             # ① 取代价最小的
    if (occ, hops) != best.get(u):
        continue                                  # ② 过期条目，跳过（见 8.2）
    if u == target or target in g[u]["near"]:
        found = u                                 # ③ 到目标或挨着目标，就是落点
        break
    for v in g[u]["near"]:
        if v == target or blocked(v):
            continue                              # ④ 不走进目标；禁行的不走
        add = 0 if mine(v) else 1                  # ⑤ 进 v 要不要占领
        nxt = (occ + add, hops + 1)
        if nxt < best.get(v, (10 ** 9, 10 ** 9)):  # ⑥ 松弛
            best[v] = nxt
            prev[v] = u
            heapq.heappush(pq, (*nxt, v))
#做什么为什么
①heappop 取出元组最小的那个Python 元组按字典序比较：先比 occ，相等再比 hops，还相等比城市 ID。城市 ID 只是让比较永远有结果，没有语义。
②和 best 对不上就丢掉同一座城可能多次入堆（每次被松弛都推一份新的）。旧的那份代价大，但还留在堆里。这叫延迟删除（lazy deletion）——不去堆里删，等它冒出来再认出来跳过。
③终止条件是「到了或挨着」目标城不必走进去，站在邻城就能打。所以有多个可能的终点，谁先从堆里冒出来谁就是最优落点（8.1 节证明）。
④不把目标城当中转目标城里有敌人，打的是它，不是要穿过它。blocked 里是禁行城和 avoid 里明确要绕开的城。
⑤代价挂在「进入的城」上见 5.2 节点权与边权。
⑥标准松弛(10**9, 10**9) 是「无穷大」，第一次见到必然更新。

4.3 BFS 是 Dijkstra 的特例

如果所有边代价都是 1，Dijkstra 的堆里代价总是「一层 d 和一层 d+1」，取出顺序和 FIFO 队列完全一样，只是多付了一个 log 的堆操作费。所以 BFS 是 Dijkstra 的退化情形，反过来说 Dijkstra 是「按代价而不是按步数分层的 BFS」。沙盘里的「BFS」模式用真正的 FIFO 队列实现，可以对照观察。

5. 项目的变体：(须占领数, 步数) 字典序

教科书的 Dijkstra 代价是一个数。这里是一个二元组，比较用字典序。这是全项目最值得琢磨的设计，展开讲三点。

5.1 字典序等价于「大权重」

(occ, hops) 的字典序意味着：少占一座城，胜过少走任意多步。(0, 6) < (1, 4)——宁可绕 6 步全走本国城，也不占 1 座敌城走 4 步。

换个写法你会更熟悉：令代价 = occ × M + hops，M 取一个比任何可能的步数都大的数（比如 1000，因为图只有 95 个点，路径最多 94 步）。这时单个整数的大小比较和二元组字典序完全等价。二元组只是不用担心 M 取多大、也不会溢出。

反过来，如果你觉得「为了少占 1 座城多绕 6 步不值」，那就应该换成 occ × 3 + hops 这类加权和。字典序是一种极端的偏好表达；权重多大才「合理」是业务决策，不是算法决策。沙盘里提供了「(步数, 占领数)」这个反向字典序，可以直观看到偏好翻转后路线怎么变。

5.2 点权与边权

「进入这座城要不要占领」是城的属性（点权），而 Dijkstra 教科书上讲的是边的代价。两者怎么统一？

很简单：把点权 c(v) 摊到所有「进入 v」的边上，定义边权 w(u→v) = c(v)。因为一条路径进入每个中间点恰好一次，路径上的边权之和就等于中间点的点权之和。代码里的 add = 0 if mine(v) else 1 就是在算 w(u→v)，只看 v 不看 u。

注意方向 这样定义后，即使道路是无向的，边权也不对称了：从本国城走进敌城代价 1，从敌城走回本国城代价 0。这没有任何问题——Dijkstra 天生就是给有向图设计的，无向边只是「两条方向相反的有向边」。

5.3 禁行结点的三种来源

tankstorm/citydb.pydef fort_locked(city_id) -> bool:

    return len(s) > 1 and s[1] in "12"

# plan_route 内部
def blocked(cid):
    home = g[cid].get("home") or 0
    return cid in skip or (fort_locked(cid) and not mine(cid) and home != 21)
  • 规则禁行：别国的首都和大城。编号规律 x1xx、x2xx；黑暗联盟原属的 9101、92xx、x2010 虽然第 2 位也是 1 或 2，但 home == 21 例外。
  • 经验禁行：avoid 集合，来自 live_plan 发现「这城有打不过的人」或 walk_to 实际攻打失败。
  • 目标本身：不作为中转。

禁行在图论上就是把这些顶点从图里删掉。删掉之后目标可能不再连通，这时算法自然地耗尽堆、found 仍是 None，返回「没有通路」。这比事先判连通再搜索要省事，也不容易漏。

7. 边走边重算：live_plan 与 walk_to

到此为止的算法都假设地图信息是准的。但本地 SQLite 里的归属国可能是几天前的，城里有没有打不过的人更是只有开了面板才知道。项目分两层处理这个「已知条件不全」的问题。

7.1 live_plan：先算、再核对、再算，直到不动

tankstorm/country_war.py · live_plan()（节选）plan = citydb.plan_route(here, target, my, blocked)
for _ in range(6):
    seq = list(plan.get("路径") or [])
    changed = False
    for city in seq:
        if city in known:
            continue
        info = _open_city(sock, rec, city, my)          # type:3 开面板，不花行动力
        known[city] = info["owner"]
        citydb.record_occupy(city, info["owner"], info["userCnt"])   # 写回 city_occupy
        changed = True
        … # 城里有失败库里的人 → blocked.add(city)
    nxt = citydb.plan_route(here, target, my, blocked)
    if not changed and nxt["路径"] == plan["路径"] and nxt["须占领"] == plan["须占领"]:
        break                                         # 不动点：没学到新东西，路线也没变
    plan = nxt

这是一个不动点迭代：用当前信息算一条路 → 只核对这条路上的城（而不是全图 95 座，那太慢）→ 归属或禁行有变就重算 → 新路线上又有没核对过的城就再核对……直到一轮下来什么都没变。最多 6 轮，防止极端情况下反复摇摆。

为什么只核对路线上的城就够了？因为不在最短路上的城，它的信息变了也不会让当前路线变差；只有路线上的城变「贵」了才需要重算。这是一种惰性求值：只在需要的地方花网络请求。

7.2 walk_to：执行时受阻，避开它再算一次

tankstorm/country_war.py · walk_to()（节选）if blocked_at:
    if replanned:
        out["停止原因"] = f"{blocked_at} {cname} 重新规划后仍受阻，停止"
        return out
    nxt = walk_to(rec, sock, config, target, sweep=sweep, beat=beat,
                  avoid=set(avoid or ()) | {blocked_at}, replanned=True)

规划是纸上谈兵，走起来才知道城里有人打不过。walk_to 沿路线逐城执行：本国城直接走，敌城先 farm_city 把人打空再占领。哪座城打不下来，就把它加进 avoid，从当前位置重新规划一次（不是从原起点，人已经走了几步了），再走。第二次还受阻就停手，把决定权交回给人。

为什么只重算一次 每次重算都可能引导玩家去打另一座城，每打一次都要烧行动力。无限重试的下场是行动力归零、人被遣返首都。工程上「失败两次就停」比「一直试到成功」更安全，这个项目里有太多这种被烧掉的勋章换来的注释。

7.3 这在图论里叫什么

「环境部分可观测、边走边发现新障碍、增量修正路径」是机器人导航的经典课题，对应的算法是 D* / D* Lite / LPA*。它们的精妙之处是复用上一次搜索的结果，只修补受影响的部分，而不是从头再算。

本项目没有用它们，而是直接重跑 Dijkstra。这是正确的取舍：95 个点、140 条边，一次 Dijkstra 微秒级；而一次开面板要等服务器几百毫秒。瓶颈在 I/O 不在计算，用复杂算法省计算是白费功夫。识别瓶颈在哪，比会多少算法更重要。

8. 复杂度与常见坑

8.1 「挨着目标就停」为什么是对的

标准 Dijkstra 的终点是一个顶点；这里终点是一个集合（目标城 + 它所有未禁行的邻居）。为什么第一个从堆里冒出来的集合成员就是最优落点？

因为 Dijkstra 出堆的代价单调不减（这是它的核心不变量）。集合里任何其他成员，要么还在堆里、要么还没入堆，代价都 ≥ 当前这个。所以当前这个就是集合里代价最小的。等价的教科书做法是加一个虚拟终点 T，从集合每个成员连一条零权边到 T，然后求到 T 的最短路——两种写法结果一样，代码里直接判断更省事。

8.2 延迟删除与 best 校验

Python 的 heapq 不支持「修改堆里某个元素的优先级」（decrease-key）。于是同一座城被松弛几次就入堆几次，堆里会有多份、代价各不相同的同城条目。处理办法就是出堆时和 best 比一下，对不上就是过期的，跳过。

漏掉这一步会怎样？过期条目的代价比 best 大，用它去松弛邻居不会产生更优结果，所以答案仍然正确，只是白做了工。但如果你在出堆后不检查就直接 break（比如「找到目标了」），就可能拿到一个过期的、非最优的代价。项目代码把校验放在终止判断之前，顺序是对的。

8.3 元组比较的陷阱

(0, 6) < (1, 4) 是 True，这是想要的。但如果元组里混进了 None——比如某处 best.get(v) 返回了 None 而没给默认值——Python 3 会直接抛 TypeError。代码用 (10**9, 10**9) 当默认值就是为了避免这个。另一个坑是元组末尾的城市 ID：它只是让相等代价的条目有个确定顺序，不要给它任何业务含义。

8.4 prev[here] = None 与 0 的区别

回溯路径用 while cur is not None。如果起点的「前驱」写成 0 而循环写成 while cur:，在城市 ID 是 0 的场合就会提前停。这个项目里 ID 都不是 0 所以不会出事，但写 is not None 是好习惯。项目里大量的 if not isinstance(v, int) or isinstance(v, bool) 也是同一种谨慎——协议解码出来的东西类型不可信。

8.5 复杂度

算法时间空间这张图（V=95, E=140）
BFSO(V + E)O(V)约 235 次基本操作
Dijkstra（二叉堆 + 延迟删除）O((V + E) log V)O(V + E)（堆里最多 E 份条目）约 1500 次
Dijkstra（数组线性找最小）O(V²)O(V)约 9000 次，在小图上其实也没差
Floyd–Warshall（全源）O(V³)O(V²)约 86 万次，一次算完所有城市对，也只要几毫秒

算法课强调渐近复杂度，是因为 V 会到百万级。这里 V=95，任何一种都够快，选择的依据变成「哪种最不容易写错」。项目选了堆版 Dijkstra，因为它是标准写法、随手就能写对。

8.6 无向图的对称性不能靠数据保证

回看 2.2 节：city_map() 把边补成双向。can_reach(here, there) 也是两边都查：there in neighbors(here) or here in neighbors(there)。这两处都在说同一件事——数据来自别人，不要假设它满足你以为的性质。

9. 延伸阅读

A*

Dijkstra 是「盲目」向四周扩展的。如果能估计每个点到目标还有多远（启发函数 h），就可以优先扩展「看起来离目标近」的点。只要 h 不高估真实代价，A* 和 Dijkstra 一样保证最优，但少访问很多点。这张图的同心圆结构其实能给出不错的 h（环上的角度差 ÷ 20°），不过 95 个点没这个必要。

Bellman–Ford / SPFA

Dijkstra 要求边权非负。如果「走进某城反而回复行动力」这种负代价出现了，就得用 Bellman-Ford（O(VE)），它还能检测负环。本项目代价是 0 或 1，用不上。

多目标最短路（Pareto 前沿）

字典序是把两个目标强行排了先后。如果你想同时看到「占 0 座走 6 步」和「占 1 座走 4 步」两个都不错的方案让人选，就需要保留每个点上所有互不支配的代价对，这叫 Pareto 最优。代价是状态数可能爆炸，实践中常配合限界。

D* Lite / LPA*

7.3 节提过：环境变化时增量修补路径而不是重算。核心是维护一个「一致性」概念，只重新处理受影响的顶点。适合大图 + 频繁小变动，比如机器人在未知地形里探索。

最短路的其他变体

k 短路（给出前 k 条路线备选）、带资源约束的最短路（行动力总量有上限，每座城消耗不同）、时间依赖最短路（冷却时间 5/10/15 秒是随状态变的）。本项目 _commit_move 里学习冷却档位的逻辑，已经隐约有「时间依赖」的影子。

推荐材料

《算法导论》第 22–24 章（图的表示、BFS/DFS、单源最短路）；Red Blob Games 的 Introduction to A* 是最好的可视化入门；D* Lite 原论文 Koenig & Likhachev 2002。

10. 自测

不看答案先想，再点开核对。前三题可以在沙盘里验证。

1. 我是意大利（1），人在威尼斯 1301，目标是雅典 9303。项目算法给出的路线是什么？须占领几座？

雅典的邻居是热那亚 1303、贝尔格莱德 9302、布鲁塞尔 9304、加莱 9321。热那亚是本国城，所以最优落点是热那亚：1301 → 1201 → 1101 → 1203 → 1303，4 步、须占领 0 座。沿外环 1301 → 9301 → 9302 只要 2 步但须占领 2 座，字典序下输了。

2. 上一题里如果把「(占领数, 步数)」换成加权和 3·occ + hops，哪条路赢？

本国路：3×0 + 4 = 4。外环路：3×2 + 2 = 8。仍是本国路。要让外环路赢，权重得降到 occ 系数 < 1，也就是「占一座城比走一步还便宜」，显然不符合游戏实际。这说明字典序在这张图上其实和大多数合理权重结论一致，差别只出现在边界情况。

3. 为什么魔多军团 NPC 城（如 12010）永远不会出现在路径中间，只能是目标？

它们的度是 1——只连着一座大城。经过一个度为 1 的顶点意味着从它进来又从它出去，走的是同一条边，这条路径去掉这两步会更短。Dijkstra 自然不会选它当中转。另外它们的编号第 2 位是 2，但 home == 21，所以并不禁行——如果它是目标，可以打；如果某天它成了别人的落点，规则上也允许。

4. 把 if (occ, hops) != best.get(u): continue 这行删掉，结果会错吗？会慢吗？

结果不会错：过期条目的代价 ≥ best[u]，用它松弛不会产生任何更新。但会慢——每个过期条目都要把 u 的所有邻居再扫一遍。在这张图上感觉不到；在百万级图上就是数倍的差距。另外，如果终止判断写在校验之前，就有可能用过期代价「找到」目标，这才是真正的错误。

5. live_plan 为什么只核对路线上的城，不核对全图？如果某座不在路线上的城被本国占了，会不会错过一条更好的路？

会错过。live_plan 只保证「当前这条路上的信息是新的」，不保证全局最优。它的取舍是：一次开面板几百毫秒，95 座城全核对要一分钟，而路线上通常只有 4–8 座。要弥补这个盲区，靠的是别的地方（--watch-cities 常驻刷新、每次打人顺手 record_occupy）持续把归属记录喂进 city_occupy 表。这是「增量维护世界模型」的思路，而不是「每次决策前全量刷新」。

6. 如果规则改成「占领一座城要花 5 点行动力、走进本国城花 1 点，行动力总量有限」，还能用现在的算法吗？

如果只是问「行动力花得最少的路」，可以：边权改成 5 或 1，还是单一非负权重的 Dijkstra。如果问「在行动力不超过 N 的前提下步数最少」，这就是带资源约束的最短路，是 NP 难的一般问题；但因为 N 很小（几百）可以把「剩余行动力」加进状态 (城市, 剩余行动力) 做分层图 Dijkstra，状态数 95 × N，仍然很快。
